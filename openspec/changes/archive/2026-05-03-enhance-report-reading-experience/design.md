## Context

当前 NextInAI 的 Web 报告区已经具备“抓取来源组、列出最近报告、展示摘要、导出 Markdown/PDF”的基础闭环，但体验仍停留在工具层：

- 默认来源过少，且过于集中在少数站点，无法覆盖主流 AI 公司、研究组织和社区讨论。
- “最近报告”使用数据表格展示，信息层级不清晰，`report_id` 这类内部字段泄露到界面，阅读体验偏后台管理而不是情报阅读。
- 抓取完成后会立刻为每篇文章生成短解读，导致“列表概览”和“深度阅读”混在一起，页面密度高但深度又不够。
- 当前详细解读更像二次摘要，不像“老师/专家带读”，无法支持用户对单篇高价值报告进行深入理解。

本次改造面向的是 Web 前端的报告工作台，但会牵动来源配置、报告 service、解读生成链路和导出链路，因此需要先定义统一的内容分层和交互模型。

约束条件：

- 第一阶段仍以 Streamlit 单体前端为主，不引入新的前后端分离架构。
- 现有抓取与摘要能力需要保留，避免推翻已有 report pipeline。
- 深度解读调用模型成本更高，不能对每篇新文章默认预生成。
- 导出体验必须与页面上的阅读层次一致，不能继续把“短摘要”和“深读正文”混成一份内容。

## Goals / Non-Goals

**Goals:**

- 扩展默认报告来源，覆盖更多 AI 公司、研究组织和社区来源，并按分组组织。
- 将“最近报告”从表格改为适合浏览和比较的阅读工作台，支持并排卡片、展开/折叠和来源筛选。
- 将报告内容拆成两层：列表概览层和按需生成的深度带读层。
- 让深度带读由用户显式点击触发，生成更长、更结构化、更像专家逐段讲解的内容。
- 为概览报告和单篇深度带读都提供导出能力，且导出内容与页面展示层级保持一致。

**Non-Goals:**

- 本次不重构整个 Chat/Agent 编排架构。
- 本次不引入数据库或异步任务队列。
- 本次不做复杂权限、多用户收藏或协作批注能力。
- 本次不承诺一次性覆盖所有 AI 社区，只定义默认高价值来源集合与扩展机制。

## Decisions

### 1. 报告能力改为“三层内容模型”

报告内容分为三层：

1. `source catalog`：来源目录，负责告诉用户“系统能抓哪些地方”。
2. `report overview`：最近报告概览，负责快速回答“最近出了什么、值不值得点开看”。
3. `deep reading`：单篇深度带读，负责回答“这篇具体在讲什么、为什么重要、有哪些值得质疑或关注的点”。

这样可以把抓取、浏览和深读三个阶段拆开，避免当前“列表里堆摘要，详情里再堆一个更短摘要”的重复感。

备选方案：

- 继续沿用单层 report detail：实现简单，但列表与详情的职责仍然混乱。
- 对每篇报告默认预生成深读：用户体验直观，但成本高、页面更重，也不适合频繁抓取。

### 2. 默认来源采用“分组目录 + 可选抓取”的组织方式

默认来源不再只有一个宽泛的 `default` 组，而是扩展为多个逻辑组，例如：

- AI 公司：OpenAI、Anthropic、Google DeepMind、Meta AI、Microsoft Research、xAI、Mistral、Cohere 等
- 开源/平台：Hugging Face、LangChain、Weights & Biases 等
- 研究/安全：研究组织博客、模型安全或评测相关站点
- 社区/论坛：LessWrong、Latent Space、官方工程博客或高价值社区栏目

实现上仍允许保留一个“默认抓取组”作为快捷入口，但系统内部必须有分组目录元数据，便于 Web 端展示和后续让用户按来源/分组抓取。

备选方案：

- 继续维护平铺来源列表：实现最省事，但扩展后会迅速失去可读性。
- 完全由用户自定义来源：灵活，但不适合当前阶段的开箱即用体验。

### 3. Web 报告区改造成“阅读工作台”而不是数据表

“最近报告”区域改为卡片式浏览：

- 每条报告以卡片展示标题、来源、发布时间、概览摘要、抓取状态和操作按钮。
- 卡片支持展开/折叠。
- 页面支持多列并排展示，优先优化“快速扫读多个候选报告”。
- 不展示 `report_id`、内部指纹或存储主键。

这一层只负责概览和进入下一步动作，不承载长篇正文。

备选方案：

- `st.dataframe` + 选中详情：实现快，但交互过于后台化。
- 单列长列表：适合移动端，但不符合本项目以桌面阅读为主的场景。

### 4. 深度带读采用“显式生成 + 持久化复用”

单篇报告的深度带读由用户主动点击生成，生成结果持久化保存，后续再次查看同一版本内容时直接复用，除非用户主动重新生成。

带读输出结构建议固定为可阅读的大纲式长文，例如：

- 这篇报告想解决什么问题
- 核心观点拆解
- 关键段落逐段带读
- 值得关注的技术/产品/商业信号
- 哪些结论可信，哪些需要保留判断
- 对使用者的实际启发

这样能把“更长”落到“更有结构和解释力”，而不是简单把摘要写长。

备选方案：

- 每次点开都重新生成：实现简单，但成本和时延不稳定。
- 深读结果只保存在前端 session：会话结束即丢失，不利于导出和复看。

### 5. 导出分为“概览导出”和“深读导出”两条链路

导出不再只围绕原始 report detail，而是与内容层级对齐：

- 概览导出：导出当前筛选条件下的报告概览集合，适合速览归档。
- 深读导出：导出某一篇报告的专家带读结果，适合深度阅读和转发。

PDF 渲染继续沿用“Markdown/结构化内容 -> HTML -> PDF”的方向，以保证长文排版优于直接文本拼接。

备选方案：

- 所有导出继续共用一份模板：实现简单，但概览和深读会互相污染。

### 6. 现有抓取后短解读保留，但定位降级为“概览摘要”

现有 `factual_summary` / `interpreted_summary` 不废弃，但它们在新模型中的角色改为概览卡片信息源，而不是最终阅读结果。真正的长篇带读单独建模，避免把现有短摘要硬拉成长文。

备选方案：

- 直接覆盖旧字段含义：会让已有导出、测试和存量数据语义漂移。

## Risks / Trade-offs

- [默认来源扩展后抓取失败率上升] → 通过来源分组、失败隔离和单来源状态展示，避免一个站点异常拖垮整组体验。
- [深度带读生成更慢] → 改为显式触发，并在页面展示“未生成 / 生成中 / 已生成”的状态。
- [长文解读质量不稳定] → 固定输出结构，明确要求逐段讲解、评论、保留判断，减少空泛总结。
- [Streamlit 并排卡片能力有限] → 采用可控的多列布局与 expander，而不是追求复杂前端组件。
- [导出模板分层后实现量增加] → 通过共享中间表示复用渲染逻辑，避免复制两套模板体系。

## Migration Plan

1. 扩展报告来源目录与来源分组元数据，保留当前默认抓取入口兼容旧操作。
2. 调整报告 service 返回模型，新增适合工作台展示的 overview 字段和深读状态字段。
3. 新增深度带读生成与持久化能力，并与现有短摘要分析结果并存。
4. 重构 Streamlit 报告页，将表格替换为卡片工作台，并接入按需生成与导出按钮。
5. 扩展导出链路，分别支持概览导出与单篇深读导出。
6. 补齐测试，验证来源扩展、卡片展示数据模型、深读生成与导出行为。

回滚策略：

- 保留现有抓取和短摘要数据结构，必要时可只关闭新深读入口和新页面布局。
- 新增深读存储使用独立记录，不覆盖原始 `analysis_results` 语义。

## Open Questions

- 默认来源第一批是否要区分“稳定来源”和“实验来源”，避免一开始就把低稳定性社区源混进默认抓取。
- 深度带读是否需要支持“重新生成”按钮和版本号，以应对 prompt 升级后的结果刷新。
- Web 端是否要在本次改造里同时加入“只抓某一个来源/某一类来源”的显式操作入口。
