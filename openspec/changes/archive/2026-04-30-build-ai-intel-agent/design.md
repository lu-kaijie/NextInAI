## 背景

该项目是一个从 0 到 1 的 Python AI Agent，用于持续追踪 AI 领域高价值信息，并把原始更新转化为可消费的情报。输入源包括 GitHub 仓库、GitHub 热门项目以及 AI 公司或社区发布的博客、公告和报告；输出包括主动查询结果、周期性 digest 和通知。

当前仓库仍处于初始化阶段，没有现成的数据模型、任务调度、通知通道或内容分析链路，因此本次设计需要同时定义项目骨架、采集层、分析层、交付层和最小可行的数据持久化方案。第一版产品将以 CLI 为唯一主要入口，输出偏快讯型但要求解释清楚、篇幅适中。系统需要优先保证可扩展性和可观察性，因为后续一定会继续增加数据源、通知渠道和分析策略。

约束条件：
- 第一阶段以 Python 单体服务为主，避免过早拆分多服务。
- 外部依赖会受到 API 限流、网页结构变化和模型成本波动影响。
- 内容采集与摘要生成必须支持幂等、去重和重跑，否则定时任务会快速失控。
- 报告生成需要兼顾“快”和“准”，不能只做机械摘要。

## 目标 / 非目标

**目标：**
- 建立统一的情报处理流水线：采集、标准化、去重、分析、汇总、通知。
- 支持用户订阅 GitHub 项目，并查看最近一段时间发生了什么变化。
- 支持发现和解读一段时间内热门的 AI GitHub 项目。
- 支持抓取和解读 AI 公司、研究组织或论坛发布的报告类内容。
- 支持按计划生成日报或周报，并通过统一通知层以邮件和 Webhook 投递。
- 支持将生成结果导出为 Markdown 与 PDF，满足“看”和“转发/归档”两类场景。
- 保留后续扩展空间，允许新增内容源、通知渠道和用户偏好规则。

**非目标：**
- 本阶段不做复杂多租户权限系统。
- 本阶段不做完整 Web 前端产品，优先提供 CLI/消息投递闭环。
- 本阶段不做高频实时流式监控，目标是分钟级到小时级的情报更新。
- 本阶段不覆盖所有 AI 信息源，只先覆盖最核心的 GitHub 与报告源。

## 关键决策

### 1. 采用 Python 单体 + 模块化边界

系统以单仓库、单服务形态实现，但按模块划分为 `collectors`、`pipelines`、`analyzers`、`digests`、`notifiers`、`storage`、`scheduler`。这样可以在早期保持开发速度，同时保留未来把采集和通知拆开的可能性。

备选方案：
- 多服务架构：扩展性更强，但对当前阶段过重。
- 脚本集合：启动更快，但后续会因为共享模型、调度和状态管理混乱而迅速失控。

### 2. 统一内容归一化事件模型

所有来源先转换成统一的 `SourceEvent` / `ContentItem` 表达，包括来源、标题、URL、发布时间、原始摘要、正文抓取状态、标签和去重指纹。摘要与解读结果再写入 `AnalysisResult`，通知记录写入 `DeliveryRecord`。这样可以让 GitHub 更新、热门项目和报告解读复用同一条处理链路。

备选方案：
- 为每个数据源建立独立模型：实现简单，但横向聚合和统一查询会非常痛苦。

### 3. CLI-first 交互方式

第一版只提供 CLI 命令入口，例如订阅仓库、拉取趋势榜、生成报告、导出 Markdown/PDF、触发通知发送。CLI 会直接调用应用服务层，而不是先做 HTTP API；等需求稳定后，再视情况把服务层暴露成 API 或 Web 界面。

备选方案：
- 先做 Web UI：更直观，但会显著拖慢 MVP 交付。
- 先做 API：接口更通用，但当前用户价值不如直接可用的 CLI 高。

### 4. 调度与采集解耦

调度器只负责触发任务，例如“抓取订阅仓库更新”“刷新今日趋势”“生成日报”；具体逻辑由独立 job handler 执行。推荐使用 APScheduler 或 Celery 的轻量模式起步，优先选能在单进程和未来后台 worker 间平滑迁移的方案。

备选方案：
- 纯 cron + CLI：早期可用，但不利于状态跟踪、失败重试和统一配置。

### 5. 分层分析链路：规则优先，LLM 增强

采集后的内容先做结构化提取和启发式过滤，再进入 LLM 生成解释性摘要。对于 GitHub 更新，第一版重点归纳“新增功能、主要改进、问题修复”三类变化；对于趋势项目，优先提取 README、主题标签、star 增长和近期活跃度，并形成偏榜单速览风格的简明解读；对于报告内容，优先提取摘要段落、目录和关键结论。LLM 负责“解释为什么重要”，而不是替代所有基础解析。

备选方案：
- 全量原文直接丢给 LLM：开发快，但成本高、稳定性差、幻觉风险更大。
- 完全规则化：成本低，但解读质量和泛化能力不足。

### 6. 热门榜单以排行榜口径优先

热门项目能力优先围绕“当天或某时间窗内 star 增长最多或榜单最热的前 N 个仓库”展开，而不是一开始做复杂的长周期研究评分模型。第一版默认输出前 10 名，核心价值是快速回答“这些项目分别是干什么的”。

备选方案：
- 自定义复杂热度评分：表达力更强，但早期解释成本高、用户不易建立预期。
- 完全照搬 GitHub Trending 页面：可实现，但可配置性和时间窗支持较差。

### 7. 通知系统做成渠道适配器

统一定义 `NotificationMessage` 和 `NotificationTarget`，让日报、趋势提醒和订阅更新都通过同一个交付接口发送。第一阶段直接支持邮件和 Webhook；其他渠道以 adapter 方式新增。

备选方案：
- 每个功能自己发通知：短期简单，但无法统一重试、审计和偏好控制。

### 8. 导出格式统一由渲染层负责

报告正文先生成统一的结构化简报文档，再分别渲染为 Markdown 和 PDF。这样可以避免为不同输出格式维护两套报告模板，并且后续增加 HTML 或消息卡片时也能复用同一份中间表示。

备选方案：
- 直接分别生成 Markdown 和 PDF：实现快，但模板重复和格式漂移风险高。

### 9. 持久化优先选本地文件存储

第一版面向个人使用，优先使用本地文件存储而不是数据库。`data/` 目录下按资源类型拆分 JSON 文件，分别保存订阅配置、采集检查点、内容项、分析结果、简报记录、投递记录和任务状态；导出的 Markdown/PDF 则继续放在 `artifacts/`。这样可以降低运维和配置成本，同时仍然满足个人工具的可追踪、可恢复和可扩展需求。

备选方案：
- 直接上数据库：在个人使用阶段收益有限，反而增加初始化和迁移成本。
- 完全不落盘：实现更快，但无法支持去重、增量抓取和失败恢复。

## 风险 / 权衡

- [GitHub API 限流或权限不足] → 对公共数据优先使用缓存、ETag、分页增量抓取，并为高频任务增加退避与重试。
- [网页/报告源格式不稳定] → 采集器分源实现，正文抽取失败时保留原始链接并降级为元信息摘要。
- [LLM 解读偏差或幻觉] → 明确区分“原始事实摘要”和“解释性分析”，输出中保留来源链接与证据字段。
- [通知噪音过高] → 支持频率控制、去重和 digest 聚合，默认少打扰而不是每条都推。
- [单体架构后续膨胀] → 强制模块边界与统一接口，避免业务逻辑散落在调度器或渠道适配器中。

## 迁移计划

1. 初始化项目骨架、配置管理、数据模型和本地运行方式。
2. 先打通 GitHub 订阅追踪与 digest 生成最小闭环。
3. 增加热门项目分析能力，复用同一分析和通知框架。
4. 增加报告采集与解读能力，补全文本抓取与内容解析。
5. 接入邮件和 Webhook 两个通知渠道，启用定时任务。
6. 基于真实使用反馈再决定是否拆分 worker、引入队列或增加 UI。

回滚策略：
- 每个能力按模块独立开关控制。
- 通知渠道异常时可只停用发送，不影响采集与报告生成。
- 新数据源上线先以影子模式运行，仅写库不推送。
