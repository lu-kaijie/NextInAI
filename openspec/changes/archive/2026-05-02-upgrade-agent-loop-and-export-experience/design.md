## Context

当前 NextInAI 已经具备本地 CLI、Streamlit 前端、受控工具层、报告抓取、热门榜分析、简报生成与任务调度能力，但交互架构仍然存在明显割裂：

- chat 的语义理解主要依赖硬编码关键词匹配，扩展新动作时需要不断追加分支；
- 网页端很多功能是“按钮直接调 service”，chat 则走另一套入口，能力对齐靠人工维持；
- GitHub trending 的时间窗口目前只暴露 `daily / 7d / 30d`，但真实能力边界没有被系统化定义；
- 报告浏览偏“批量抓取后列表展示”，缺少按来源筛选、单条深读与统一导出抽象；
- 导出能力目前聚焦 digest，未覆盖 GitHub 分析结果和报告详细解读。
- 现有 PDF 导出虽然可用，但排版质量较弱，标题层级、段落间距、列表样式和长文本换页体验都不理想。

这次变更是跨 `agents`、`harness`、`services`、`web` 的架构性调整，适合先落设计再实施。

## Goals / Non-Goals

**Goals:**

- 用 agent loop + tool calling 替换 chat 主路径上的硬编码意图路由。
- 建立统一 capability 层，让 chat 与网页端调用同一组后端动作。
- 明确定义 GitHub trending 的能力边界、查询粒度与降级策略。
- 重构报告浏览体验，支持来源筛选、摘要查看、单条详细解读与导出。
- 把 GitHub 摘要、报告摘要、详细解读纳入统一导出体系。
- 修复 PDF 导出的版式质量，确保导出结果能直接阅读，而不是仅“技术上生成成功”。
- 明确传统 CLI 只承担脚本化、验收和降级职责，不追求与 chat / web 做机械式全量同步。

**Non-Goals:**

- 本次不引入数据库或多用户系统。
- 本次不追求开放式 autonomous agent，自由联网、自主规划仍保持受控。
- 本次不承诺 GitHub trending 一定支持任意历史时间窗口；如果官方接口不支持，应明确降级而不是伪造能力。
- 本次不切换 Streamlit 技术栈。
- 本次不为每个新能力都补一套对等的传统 CLI 参数入口。

## Decisions

### 1. Chat 从“关键词路由”升级为“单路径受控 agent loop”

决策：
- 保留现有 harness 受控执行模型，但将 `AssistantAgent` 的主路径替换为 LLM 驱动的工具选择与多步 tool-calling loop。
- 不再保留关键词路由 fallback，也不保留同一功能的双轨判定逻辑。
- 通过工具 schema、会话状态、参数校验和确认流约束，限制 agent 只能在允许范围内规划和调用。

原因：
- 这样能真正让工具选择由模型负责，而不是表面上有 planner、底层仍靠硬编码关键词分支驱动。
- 删除 fallback 后，系统复杂度更低，行为路径更清晰，也更符合项目的 agent / harness 定位。
- 保留现有 `ExecutionEngine`、`ToolRegistry`、`SessionStateStore`，避免把项目改造成失控的通用聊天机器人。

备选方案：
- 继续堆关键词分支：实现快，但复杂度会持续上升。
- 完全自由 agent：灵活，但不符合当前个人工具和可控执行定位。

### 2. 网页与 Chat 共享同一 capability service

决策：
- 为“热门查询、报告浏览、详细解读、导出、任务操作”建立统一 service / tool 接口。
- Streamlit 页面不直接拼接零散 service 调用，而是复用 capability 层或工具层。
- 传统 CLI 仅在这些能力中选择高价值、适合脚本化的部分暴露，不追求逐项镜像。

原因：
- 避免“页面能做但 chat 不能做”或“chat 能做但页面没有入口”的分裂。
- 便于后续扩展网页端或其他交互层。
- 很多依赖上下文的交互能力，例如“继续展开上一条结果”“把刚才那份分析导出 PDF”“基于当前结果创建任务”，天然更适合 chat / web，而不是堆成超长 CLI 参数。

备选方案：
- 保持网页端和 chat 各自直接调用 service：短期省事，长期难维护。

### 3. Trending 能力先做“能力探测 + 真实边界声明”

决策：
- 实施前先确认 GitHub 官方 Trending 页面/API、Search API、第三方替代口径分别支持什么。
- 产品层输出必须明确区分：
  - 官方稳定支持
  - 近似替代实现
  - 当前不支持

原因：
- 用户明确要求“和官方 trending 一致”，因此不能为了满足任意时间窗口而伪造同口径能力。

备选方案：
- 直接拿 GitHub Search 按 stars/filter 拼任意窗口：实现容易，但口径会偏离官方 trending。

### 4. 报告浏览分成“来源列表 -> 文章列表 -> 解读详情”

决策：
- 新增来源维度视图，而不是只做一次批量抓取结果展示。
- 为每条报告保留摘要视图和详细解读视图，支持前端点击展开与 chat 深挖。

原因：
- 用户希望“可以选择哪个公司、看最近报告、点进去详细解读”，这本质上需要对象化浏览，而不是纯文本输出。

备选方案：
- 继续只展示最近抓到的解读列表：简单，但无法满足定向浏览。

### 5. 导出抽象统一到内容对象，而不是仅 digest

决策：
- 导出能力按“内容类型”抽象，至少覆盖：
  - GitHub 仓库更新摘要
  - 热门榜分析
  - 报告摘要
  - 报告详细解读
  - digest / briefing
- 统一支持 Markdown，PDF 作为可选格式复用已有导出器。

原因：
- 目前导出只服务 digest，用户已经把“导出”视为所有分析结果的共性能力。

备选方案：
- 每个模块各自实现导出：短期可行，但格式和存储会失控。

### 6. PDF 导出质量按“阅读产物”标准重构

决策：
- 将 PDF 导出质量视为产品能力而不是附属功能，统一处理标题层级、段落间距、列表缩进、分页、长文本换行和元信息展示。
- 优先在现有导出器基础上增强版式规则，而不是简单替换文件格式。

原因：
- 用户已经明确指出现有 PDF “格式太差”，说明当前问题不是有没有导出，而是导出结果不可直接消费。

备选方案：
- 保持当前实现，仅建议用户导出 Markdown：不能满足产品目标。
- 直接引入 HTML 转 PDF 渲染链：效果可能更好，但实现复杂度和依赖成本更高，当前版本先不作为首选。

## Risks / Trade-offs

- [LLM tool calling 替换硬匹配后不稳定] → 不再保留规则 fallback，而是通过更严格的工具 schema、参数约束、引用解析和确认流来收敛不稳定性。
- [Trending 任意时间窗口无法与官方口径一致] → 在 spec 中明确能力边界，并把近似查询标识为替代模式。
- [网页与 chat 全量对齐会带来接口膨胀] → 先统一高频能力，围绕 capability 对象组织接口，而不是暴露碎片函数。
- [导出范围扩大后格式不一致] → 抽象统一的导出模型和文件命名规则。
- [PDF 版式增强后实现复杂度上升] → 先覆盖最影响阅读的结构元素，再逐步增强视觉细节。
- [报告详细解读会增加 token 与响应耗时] → 区分列表摘要与按需深读，避免默认对所有文章做重解读。

## Migration Plan

- 第一阶段：删除现有关键词路由主路径，改为单路径 agent loop。
- 第二阶段：抽离统一 capability service，让网页端和 chat 共用。
- 第三阶段：补充报告来源筛选、详情页与统一导出。
- 第四阶段：修复 PDF 导出版式并统一导出表现。
- 第五阶段：根据 GitHub 官方能力边界决定 trending 的产品文案与交互模式。
- 回滚策略：不再维护旧关键词路由；若后续需要调整，只修正单一路径的 agent loop 与 capability 实现。

## Open Questions

- GitHub 官方 trending 是否存在稳定 API，还是只能通过页面抓取和替代口径组合实现？
- 报告详细解读是首次抓取时就生成，还是改为“点击某条后按需生成/补全”？
- 统一导出是否需要加入 HTML，还是先只保留 Markdown/PDF？
- PDF 质量修复是否需要同时引入封面、目录或页脚，还是先聚焦正文可读性？
- chat 与页面共享 capability 后，是否需要把“任务创建”也补成独立表单，而不是主要依赖 chat？
